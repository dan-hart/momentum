# Momentum feature ledger

Updated: 2026-10-13. See [AGENTS.md](../AGENTS.md) for policy and status definitions.
Every row has an independent Linux, macOS, iOS, and Android status. `Implemented`
is deliberately not a claim of complete native verification. Baseline entries below
are seeded from the existing source/specifications and recorded acceptance, not a
fresh audit of every legacy feature. Their evidence is dated in [PROGRESS.md](PROGRESS.md).
Split a row into stable child IDs if its sub-capabilities progress differently.

## Existing capabilities and mobile requirements

The native iOS app is now explicitly requested through macOS parity. Its
[architecture and acceptance proposal](superpowers/specs/2026-09-16-ios-parity-design.md)
maps the rows below to native iOS behavior. Rows remain Planned until implementation
starts; inspecting source and writing a design do not verify an app.
The [iOS acceptance checklist](IOS-PARITY-CHECKLIST.md) expands those rows into
individual task actions, settings, native integrations and required evidence.

The native Android app is now in local implementation through iOS capability parity.
Its [approved design](superpowers/specs/2026-10-10-android-parity-design.md) and
[Android acceptance checklist](ANDROID-PARITY-CHECKLIST.md) record every feature ID,
native differences, incomplete work and remaining verification. Android entries below
are Implemented or In progress for existing code; scoped tests do not establish broad
Verified status. F-Droid admission, store release and reproducibility are separate gates.

Unless a row says otherwise, mobile Planned means: expose the same Rust behavior
through native, accessible mobile UI; verify persistence, offline operation, and
platform interaction. It does not mean a mobile app or binding already exists.
